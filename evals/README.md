# Eval плагина orchestra

Проверяет плагин целиком: тимлид в headless-сессии Claude Code решает задачу в маленьком проекте, а результат оценивает код — приёмочные тесты, git и журнал. Нужен, чтобы любое изменение плагина (карта проекта, другая модель у роли, правка инструкций) можно было сравнить «до» и «после» по качеству и цене, а не на глаз.

## Кейсы

| кейс | уровень | что проверяет |
|---|---|---|
| `s-bugfix-promo` | S | исправление бага: двойная скидка по промокоду; регрессионный тест |
| `s-cart-remove` | S | небольшая фича по точной спецификации: `Cart.remove` |
| `m-export-csv` | M | новый модуль по спецификации: полный путь с ревью и архитектурой |
| `m-promo-rules` | M, трудный | много точных требований с подвохами: округление до потолка, исключённые товары, границы дат, совместимость и хешируемость `PromoCode` |

Все кейсы — на проекте `fixtures/shop` (stdlib + pytest). Устройство кейса:

```
cases/<имя>/
├── case.json    # задача, уровень, must_not_change, min_new_tests, timeout_s
├── overlay/     # что наложить на фикстуру до прогона (необязательно)
├── hidden/      # приёмочные тесты: агенты их не видят, копируются после прогона
└── solution/    # эталонное решение — только для self-check
```

## Как проходит прогон

1. Копия фикстуры + overlay → git-репозиторий, один коммит в `main`, автор `Eval User <eval@example.com>`.
2. `.orchestra/config.json` с `"mode": "cloud"`: тимлид коммитит сам, без вопросов.
3. `claude -p "/orchestra:teamlead <задача>"` с плагином из `plugins/orchestra`, без пользовательских настроек и MCP (`--setting-sources project,local --strict-mcp-config`), без plan mode и вопросов. В системный промпт добавляется: согласования считаются одобренными, пуш пропустить.
4. Проверки кодом:

| проверка | обязательная | что значит |
|---|---|---|
| `claude_ok` | да | сессия завершилась без ошибки |
| `hidden_tests` | да | приёмочные тесты кейса зелёные |
| `project_tests` | да | все тесты проекта зелёные, включая написанные тестером |
| `committed` | да | коммиты в рабочей ветке, `main` не тронут, автор и коммиттер — пользователь, без приписок о Claude, незакоммиченных правок нет |
| `untouched` | да | файлы из `must_not_change` не изменились |
| `new_tests` | нет | тестер добавил не меньше `min_new_tests` тестов |

Прогон засчитан, если прошли все обязательные проверки.

## Метрики

- **успешно** — доля засчитанных прогонов;
- **pass^k** — вероятность, что задача решена во всех k попытках подряд (оценка из τ-bench: C(c, k) / C(n, k), где n попыток, c успешных). Для агента это честнее одного удачного прогона: pass^1 = 0,9 при pass^3 = 0,5 значит, что плагин часто, но нестабильно справляется;
- **$ и время** — из ответа Claude Code (`total_cost_usd`, включая сабагентов);
- **токены по ролям** — из журнала `.orchestra/reports/usage.jsonl`: вход всего, чтение кеша, выход, сколько раз роль искала по проекту (Read/Grep/Glob) — по последнему видно эффект карты проекта;
- **события хука** — сколько раз агенты упирались в границы ролей.

## Запуск

```bash
python3 evals/run_evals.py self-check                         # кейсы корректны: без Claude и без затрат
python3 evals/run_evals.py run --cases s-bugfix-promo -k 1    # один прогон, для проверки
python3 evals/run_evals.py run -k 3 --max-budget-usd 15       # все кейсы по 3 раза
python3 evals/run_evals.py run --model sonnet -k 3            # другая модель тимлида
```

Результаты — в `evals/results/<время>/`: `summary.md`, `summary.json` и по папке на прогон (`result.json`, ответ Claude, `git-log.txt`, `diff.patch`, копия `.orchestra/`). `--keep` оставляет рабочую копию проекта (путь — в `workdir.txt`).

**Это стоит денег:** тимлид и ревьюер работают на Opus, кейс M проходит полный путь с ревью и архитектурой. Начинайте с одного кейса и `-k 1`, ставьте `--max-budget-usd`. По умолчанию `--permission-mode bypassPermissions`: агенты работают во временной папке без подтверждений — запускайте на своей машине или в контейнере.

## Сравнение «до» и «после»

```bash
python3 evals/run_evals.py run -k 3 --out evals/results/before
# ...изменение плагина...
python3 evals/run_evals.py run -k 3 --out evals/results/after
python3 evals/run_evals.py compare evals/results/before/summary.json evals/results/after/summary.json
```

Меняйте одно за раз: доля успешных не должна упасть, а цена и токены нужной роли — должны.

## Новый кейс

1. Папка в `cases/` с `case.json`, `hidden/` и `solution/` (и `overlay/`, если нужна другая стартовая версия проекта). Задачу формулируйте как тикет с точным интерфейсом: приёмочные тесты импортируют его по имени.
2. `python3 evals/run_evals.py self-check` — на исходном проекте приёмочные тесты должны падать, на эталоне всё должно проходить. Этот же self-check идёт в CI.
